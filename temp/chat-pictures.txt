Контекст: один чат на троих — абонент (ЛК), оператор (helpdesk), инженер

==============================================================================
0. КРАТКИЙ ВЕРДИКТ (что сломано у абонента сейчас)
==============================================================================

1) Браузер в ЛК запрашивает картинку как:
     https://test.wifitochka.ru/IMG-20240604-WA0024.jpg   → 404
   вместо:
     https://test.wifitochka.ru/media/...                 → ожидаемый путь

   Причина: в API/БД пришёл «голый» путь (имя файла без /media/), а фронт ЛК
   сделал только "/" + file_path → URL в корень сайта, а не в /media/.

2) Даже корректный /media/{hash}.webp с диска ЛК работает (200), а файлы
   оператора/инженера с другого диска — нет, пока nginx ЛК не умеет fallback
   на общий том и/или uploads helpdesk.

3) Целевая схема: ВСЕ НОВЫЕ вложения чата писать в общий том
   /opt/www/skystream_chat_media под URL вида /media/chat/...
   Старые плоские /media/{hash}.* остаются через nginx fallback.


==============================================================================
1. УЧАСТНИКИ И ДИСКИ
==============================================================================

Три приложения на одном сервере, один чат (users.user_mail + вложения).

┌──────────────┬─────────────────────────────┬────────────────────────────────┐
│ Кто          │ Docker volume (типично)     │ Физический путь на хосте       │
├──────────────┼─────────────────────────────┼────────────────────────────────┤
│ ЛК           │ /app/uploads                │ /opt/docs/lk_files             │
│ ЛК (чат)     │ /app/uploads/chat           │ /opt/www/skystream_chat_media  │
│ Helpdesk     │ /app/uploads                │ …/helpdesk/uploads             │
│ Helpdesk чат │ /app/uploads/chat           │ /opt/www/skystream_chat_media  │
│ Инженер      │ (свой MEDIA + chat mount)   │ /opt/www/skystream_chat_media  │
│              │                             │ + fallback на lk_files /        │
│              │                             │   helpdesk/uploads             │
└──────────────┴─────────────────────────────┴────────────────────────────────┘

Docker ЛК (как сейчас):
  volumes:
    - /opt/docs/lk_files:/app/uploads
    - /opt/www/skystream_chat_media:/app/uploads/chat

Docker helpdesk:
  volumes:
    - ./uploads:/app/uploads
    - /opt/www/skystream_chat_media:/app/uploads/chat

Правило:
  URL  /media/X          ↔  файл MEDIA_ROOT/X
  URL  /media/chat/Y     ↔  файл MEDIA_ROOT/chat/Y  = хост skystream_chat_media/Y

Картинка в <img src="/media/..."> всегда запрашивается с ДОМЕНА зрителя
(ЛК / helpdesk / инженер). Nginx каждого домена сам отдаёт файл с диска.
Бэкенд helpdesk НЕ проксирует байты картинки в чужой домен.


==============================================================================
2. ФОРМАТЫ URL (контракт)
==============================================================================

2.1. Канонический (новые загрузки всех участников)
------------------------------------------------------------------------------
  /media/chat/{subscriber_id}/{scope}/{safe_name}

  где:
    subscriber_id — id абонента (users.user.id = chat_id)
    scope         — id тикета ИЛИ служебный сегмент:
                      - числовой ticket_id (инженер / тикет-чат)
                      - "cs" — сообщения оператора из helpdesk /chat
                      - иное по согласованию, но НЕ пусто
    safe_name     — безопасное имя на диске, например:
                      photo_1710000000_a1b2c3d4e5.webp
                      1786610482_a46b51a288_IMG-20240604-WA0026.webp

  Пример (реальный рабочий):
    /media/chat/13807/562/1786610482_a46b51a288_IMG-20240604-WA0026.webp
    → диск: /opt/www/skystream_chat_media/13807/562/1786610482_….webp

2.2. Легаси плоский (старые загрузки ЛК и старый helpdesk)
------------------------------------------------------------------------------
  /media/{hash}.webp
  /media/{uuid}.jpg

  Физически чаще всего:
    ЛК:       /opt/docs/lk_files/{hash}.webp
    helpdesk: …/helpdesk/uploads/{hash}.webp

  Оба формата должны открываться у ВСЕХ участников через nginx fallback
  (см. раздел 7). Новые загрузки в плоский формат НЕ делать.

2.3. ЗАПРЕЩЁННЫЕ / ошибочные URL
------------------------------------------------------------------------------
  /IMG-20240604-WA0024.jpg          — без /media/ → 404 корень сайта
  media/chat/...                    — без ведущего /
  IMG-….jpg                         — относительный путь от текущей страницы
  https://helpdesk…/media/...      — чужой домен (CORS/куки/nginx не нужны;
                                      используйте относительный /media/...
                                      на своём хосте)

Правило нормализации (обязательно на бэке ЛК при отдаче API и при записи):

  def normalize_media_url(p: str | None) -> str | None:
      if not p or p in ("0", ""):
          return None
      p = p.strip()
      if p.startswith("http://") or p.startswith("https://"):
          return p
      if p.startswith("/media/"):
          return p
      if p.startswith("media/"):
          return "/" + p
      # голое имя или chat/... без префикса
      return "/media/" + p.lstrip("/")

На фронте ЛК:
  - В src/href класть ТОЛЬКО нормализованный file_path из API.
  - НИКОГДА не строить URL из original_filename.
  - Если file_path без ведущего / — не делать "/" + name; звать нормализацию
    или считать багом бэка.


==============================================================================
3. БАЗА ДАННЫХ (общая)
==============================================================================

3.1. users.user_mail — сообщение
------------------------------------------------------------------------------
  id, text, user_chat, person_type, user_id, …
  file_new   VARCHAR — ЛЕГАСИ одиночный путь к файлу
                       ('0' / '' = нет файла)
                       Значение должно быть полным media-URL:
                       /media/chat/... или /media/{hash}.ext
  real_file  TEXT    — оригинальное имя файла (для UI), НЕ путь для <img>

  person_type автора:
    'user'      — абонент (ЛК)
    'skystream' — оператор / инженер helpdesk-контура
    'partner' / 'tech' / 'bot' — прочие

3.2. users.user_mail_attachments — вложения (предпочтительно)
------------------------------------------------------------------------------
  id, msg_id → user_mail.id
  file_path         VARCHAR(512)  — ОБЯЗАТЕЛЬНО полный URL /media/...
  original_filename VARCHAR(512)  — имя для подписи (можно кириллицу)
  file_ext          VARCHAR(32)   — ".webp" / "webp" / ".pdf" (нормализуйте)
  file_size_bytes   INT

  У одного сообщения может быть несколько строк.
  Новые загрузки ЛК: писать СЮДА (и при желании дублировать первый путь
  в file_new для совместимости со старыми клиентами).

3.3. Что отдавать в JSON чата (контракт для фронта ЛК)
------------------------------------------------------------------------------
Сообщение:
{
  "msg_id": 123,
  "text": "...",
  "file_path": "/media/chat/13807/cs/….webp",   // или null; УЖЕ нормализован
  "attachments": [
    {
      "id": 55,
      "file_path": "/media/chat/13807/562/….webp",  // ТОЛЬКО это в <img src>
      "original_filename": "IMG-20240604-WA0024.jpg",
      "file_ext": ".webp",
      "file_size_bytes": 234512,
      "is_image": true
    }
  ]
}

Правила сборки на бэке:
  1) Прочитать attachments по msg_id.
  2) Если file_new валиден и ещё нет такого file_path в attachments —
     добавить синтетическое вложение (id=0 допустим).
  3) Каждый file_path прогнать через normalize_media_url.
  4) is_image = true, если расширение пути/имени/file_ext в
     {jpg,jpeg,png,gif,webp,bmp} (с точкой или без).


==============================================================================
4. КАК СЕЙЧАС ГРУЗЯТ УЧАСТНИКИ
==============================================================================

4.1. Абонент (ЛК) — текущее поведение (проблемное)
------------------------------------------------------------------------------
  Типично пишет в корень /app/uploads (= lk_files):
    файл:  /opt/docs/lk_files/{hash}.webp
    в БД:  /media/{hash}.webp   ← ок по форме URL
  либо (баг):
    в БД:  IMG-….jpg / только original_filename → фронт собирает /IMG-….jpg

  Volume chat смонтирован, но новые файлы часто НЕ попадают в /media/chat/.

4.2. Оператор helpdesk (/chat) — актуальное поведение
------------------------------------------------------------------------------
  POST сообщения с картинкой (только image/*, ≤ 15 МБ, magic-check).
  Сохранение:
    MEDIA_DIR/chat/{subscriber_id}/cs/{safe_base}_{stamp}_{uniq}{ext}
  В БД (file_new):
    /media/chat/{subscriber_id}/cs/{safe_base}_{stamp}_{uniq}{ext}
  real_file = оригинальное имя пользователя.

  Текст и картинка в одном сообщении: либо текст, либо картинка (не оба).
  Не-картинки в этом эндпоинте не принимаются.

4.3. Инженер / тикет-чат helpdesk
------------------------------------------------------------------------------
  Целевой путь: /media/chat/{user_id}/{ticket_id}/…
  Часто двухфазно: upload → tmp → finalize → user_mail_attachments
    или tracker_message_attachments.
  Допускаются: изображения, PDF, Word, Excel, CSV; лимит 15 МБ; magic-check.
  Клиент может сжимать фото в WebP до отправки.

4.4. Старый операторский helpdesk
------------------------------------------------------------------------------
  Писал плоско: /media/{hash}.webp в helpdesk/uploads.
  Такие URL ещё живут в БД — nginx fallback обязателен.


==============================================================================
5. ЧТО ДОЛЖЕН ДЕЛАТЬ ЛК ПРИ ЗАГРУЗКЕ (ТРЕБОВАНИЕ)
==============================================================================

5.1. Целевой путь на диске
------------------------------------------------------------------------------
  Внутри контейнера ЛК:
    /app/uploads/chat/{subscriber_id}/{scope}/{safe_name}
  = хост:
    /opt/www/skystream_chat_media/{subscriber_id}/{scope}/{safe_name}

  В БД писать ТОЛЬКО:
    /media/chat/{subscriber_id}/{scope}/{safe_name}

  Рекомендуемый scope для чистого чата без тикета: "cs" или "lk"
  (согласовать один раз; helpdesk оператор уже использует "cs").
  Если сообщение привязано к ticket_id — использовать ticket_id как scope.

5.2. Имя файла на диске
------------------------------------------------------------------------------
  - Не хранить «как прислал пользователь» без префикса (коллизии, кириллица).
  - Схема: {safe_stem}_{unix_ts}_{uniq10}{ext}
  - safe_stem: только [A-Za-z0-9._-], остальное → _
  - Оригинальное имя — только в original_filename / real_file.

5.3. Типы и проверки
------------------------------------------------------------------------------
  Изображения: .jpg .jpeg .png .gif .webp .bmp
  Документы (если ЛК разрешает): .pdf .doc .docx .xls .xlsx .csv
  Лимит: 15 МБ на файл
  Проверка magic bytes по расширению (защита от подмены).
  Опционально: клиентское сжатие image → webp (как в helpdesk тикетах).

5.4. Запись в БД
------------------------------------------------------------------------------
  1) INSERT users.user_mail (person_type='user', user_chat=subscriber_id, …)
  2) INSERT users.user_mail_attachments (
       msg_id, file_path=/media/chat/..., original_filename, file_ext, size)
  3) Для совместимости со старыми клиентами:
       UPDATE/при INSERT file_new = тот же /media/chat/...
       real_file = original_filename
  4) Не писать в file_path / file_new голое имя файла.

5.5. Ответ API после upload
------------------------------------------------------------------------------
  Вернуть клиенту уже нормализованный file_path (/media/...), чтобы сразу
  показать превью без второго round-trip.


==============================================================================
6. ЧТО ДОЛЖЕН ДЕЛАТЬ ЛК ПРИ ОТОБРАЖЕНИИ (ТРЕБОВАНИЕ)
==============================================================================

6.1. Источник URL
------------------------------------------------------------------------------
  Для картинки:
    <img src="{attachment.file_path}" alt="{original_filename}" loading="lazy">
  Для файла:
    <a href="{attachment.file_path}" target="_blank" rel="noopener">…

  file_path — единственный источник URL.
  original_filename — только подпись / title / download-атрибут имени.

6.2. Определение «это картинка»
------------------------------------------------------------------------------
  is_image === true
  ИЛИ расширение file_path / original_filename / file_ext ∈
      jpg jpeg png gif webp bmp
  (нормализовать: "webp" и ".webp" оба ок).

  Важно: файл может называться IMG-….jpg в original_filename, а на диске
  быть .webp в file_path — превью строить по file_path, не по имени.

6.3. Легаси
------------------------------------------------------------------------------
  Если attachments пуст, но file_new / file_path сообщения заполнен —
  показать как одно вложение после normalize_media_url.

6.4. Типичный баг (исправить обязательно)
------------------------------------------------------------------------------
  ПЛОХО:
    href = file_path.startsWith("/") ? file_path : ("/" + file_path)
    // для "IMG.jpg" → "/IMG.jpg" → 404

  ХОРОШО:
    href = normalizeMediaUrl(file_path)
    // → "/media/IMG.jpg" или уже "/media/chat/…"

  Ещё лучше: нормализация только на бэке; фронт доверяет API.


==============================================================================
7. NGINX ЛК (обязательная отдача чужих файлов)
==============================================================================

Даже при идеальных URL файл должен найтись на диске домена ЛК.

Рекомендуемая схема (как у инженеров / обновлённый helpdesk):

  # 1) Общий том чата (новые файлы всех)
  location ^~ /media/chat/ {
      alias /opt/www/skystream_chat_media/;
      expires 30d;
      add_header Cache-Control "public, max-age=2592000";
  }

  # 2) Плоские /media/{hash} — сначала файлы ЛК, потом helpdesk
  location /media/ {
      alias /opt/docs/lk_files/;
      error_page 404 = @media_helpdesk;
      expires 30d;
      add_header Cache-Control "public, max-age=2592000";
  }

  location @media_helpdesk {
      # путь к uploads helpdesk на хосте — уточнить у ops
      alias /home/as/development/helpdesk/uploads/;
      expires 30d;
      add_header Cache-Control "public, max-age=2592000";
  }

Без @media_helpdesk абонент не увидит старые картинки оператора
(/media/{hash} из helpdesk/uploads).

Без location ^~ /media/chat/ абонент не увидит инженера и нового оператора.

8. МАТРИЦА «КТО КОГО ВИДИТ» (проверка приёмки)
==============================================================================

После правок ЛК (код + nginx) абонент должен видеть:

  ┌─────────────────────────────┬──────────────┬────────────────────────────┐
  │ Источник файла              │ Типичный URL │ Ожидание в ЛК              │
  ├─────────────────────────────┼──────────────┼────────────────────────────┤
  │ Свои новые (ЛК → chat/)     │ /media/chat/ │ 200                        │
  │ Свои старые (lk_files hash) │ /media/hash  │ 200 из lk_files            │
  │ Оператор новый (cs/)        │ /media/chat/ │ 200 из skystream_chat_media│
  │ Оператор старый (hash)      │ /media/hash  │ 200 через @media_helpdesk  │
  │ Инженер                     │ /media/chat/ │ 200 из skystream_chat_media│
  │ Битый путь без /media/      │ /IMG-….jpg   │ НЕ должно появляться в UI  │
  └─────────────────────────────┴──────────────┴────────────────────────────┘

Проверки curl с хоста ЛК (подставить реальные имена):

  curl -I https://test.wifitochka.ru/media/b6c204126f5cc042.webp
  curl -I https://test.wifitochka.ru/media/chat/13807/562/….webp
  curl -I https://test.wifitochka.ru/IMG-20240604-WA0024.jpg
  # последний — должен НЕ использоваться UI; сам по себе 404 нормален

9. ЧЕКЛИСТ ДЛЯ РАЗРАБОТКИ ЛК
==============================================================================

Бэкенд
  [ ] При сохранении файла писать только под /app/uploads/chat/...
  [ ] В БД file_path / file_new всегда начинаются с /media/
  [ ] Писать строку в user_mail_attachments (+ опционально file_new)
  [ ] При выдаче истории нормализовать все пути (в т.ч. легаси)
  [ ] Не отдавать original_filename как URL
  [ ] Magic-check + лимит 15 МБ + whitelist расширений

Фронт
  [ ] <img>/<a> только из file_path (нормализованного)
  [ ] is_image по file_ext / пути / флагу, не только по original_filename
  [ ] Убрать логику "/" + filename для вложений
  [ ] onerror: показать «файл недоступен», не подставлять другое имя

Ops / nginx
  [ ] location ^~ /media/chat/ → skystream_chat_media
  [ ] location /media/ → lk_files + fallback helpdesk/uploads
  [ ] client_max_body_size ≥ 20M
  [ ] volumes ЛК: lk_files + skystream_chat_media:/app/uploads/chat


==============================================================================
10. СВЯЗЬ С HELPDESK (для справки, не менять в ЛК)
==============================================================================

Helpdesk SPA: <img src={a.file_path}> — относительный путь на своём домене.
Helpdesk API нормализует исходящие file_path в /media/...
Оператор /chat пишет в /media/chat/{id}/cs/...
Nginx helpdesk: /media/chat/ → общий том; /media/ → lk_files → fallback uploads.

Документы в репозитории helpdesk (доп. контекст):
  temp/chat-description.txt  — общая модель чата / таблицы
  temp/send-files.txt        — двухфазная загрузка в тикетах
