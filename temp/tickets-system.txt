0. КОНТЕКСТ И РАЗДЕЛЕНИЕ ОТВЕТСТВЕННОСТИ
────────────────────────────────────────

Этот репозиторий (helpdesk) — портал оператора КС/инженера:
  • /tickets          — список тикетов (React: ChatsTab)
  • /tickets/{id}     — карточка тикета + чат (React: TicketPage)

Создание тикетов source='lk' в этом репозитории НЕ реализовано.
Тикеты создаёт внешний личный кабинет абонента (lk.wifitochka.ru / abs-flask).
Helpdesk только:
  • читает тикеты и сообщения из общей БД PostgreSQL (схема users);
  • отвечает абоненту (INSERT в user_mail);
  • управляет очередью (queue v2), эскалацией, закрытием;
  • синхронизирует v2-очередь с лентой сообщений (reconcile).

Для ТЗ абонентского чата: ЛК должен писать в те же таблицы, что helpdesk читает.
Публичный чат source='lk' хранится в users.user_mail, НЕ в users.tracker_messages.

2.1. Основная таблица чата: users.user_mail
────────────────────────────────────────────
SQLAlchemy: UserMail (app/models/users.py)

Публичная переписка абонент ↔ оператор для source='lk'.

  id              bigint PK
  text            text — тело сообщения
  date_tz         timestamptz — основная метка времени (используется в UI)
  date            bigint — legacy unix timestamp (Москва)
  updated_at      timestamptz — время редактирования

  ticket_id       bigint nullable — ПРЯМАЯ привязка к тикету (предпочтительно)
  user_chat       bigint nullable — legacy группировка чата

  id_user_from    bigint — отправитель (user_id абонента или skystream_users.id)
  id_user_to      bigint — получатель

  answer          int default 0
                  0 = от абонента, 1 = от staff (legacy, если нет person_type)
  person_type     varchar(20) nullable
                  'user'     — сообщение абонента
                  'skystream'— сообщение оператора/инженера
  user_id         bigint nullable — skystream_users.id при ответе staff

  read            enum '0'|'1' — legacy флаг прочтения
  new             int — legacy
  relay_msg_id    varchar — ID сообщения, на которое отвечают (цитата)

  file_new, real_file — legacy одиночный файл (устарело)
  ip_address      inet
  view_from, view_to, cs_answer, file — legacy

Определение «сообщение от абонента» (_MAIL_IS_CLIENT в ticket_service.py):
  IF user_id IS NOT NULL AND person_type IS NOT NULL:
    person_type = 'user' → абонент
  ELSE:
    answer = 0 → абонент

Определение «сообщение от staff»:
  person_type = 'skystream' OR answer = 1

При создании тикета в ЛК (ожидаемый контракт):
  INSERT user_mail:
    text = текст сообщения
    id_user_from = user_id абонента
    id_user_to   = 0 или системный
    answer = 0
    person_type = 'user'
    ticket_id = id нового тикета
    date_tz = NOW()

При ответе оператора (helpdesk, send_mail_reply):
  INSERT user_mail:
    text = текст
    id_user_from = operator_id (skystream_users.id)
    id_user_to   = user_id абонента (chat_id)
    answer = 1
    person_type = 'skystream'
    user_id = operator_id
    ticket_id = ticket_id
    relay_msg_id = str(reply_to_id) если цитата
    date_tz = NOW()

3. СОСТОЯНИЯ ТИКЕТА
================================================================================

Система использует ДВА независимых слоя состояния.

3.1. Workflow-статус (поле status, enum users.tracker_status)
─────────────────────────────────────────────────────────────
Константы: app/constants.py

ОТКРЫТЫЕ (TRACKER_OPEN_STATUSES):
  pending           — ожидает обработки (начальный для новых)
  open              — открыт
  in_progress       — в работе
  waiting_client    — ждём ответа абонента (после ответа staff)
  waiting_technician— ждём техника
  no_technician     — нет техника
  waiting_parts     — ждём запчасти
  waiting_logistics — ждём логистику
  cc_handover       — передача в КС
  waiting_cs        — ждём КС

ЗАКРЫТЫЕ (TRACKER_CLOSED_STATUSES):
  resolved          — решён
  closed            — закрыт
  cancelled         — отменён
  deferred          — отложен
  not_resolved      — нерешён

ОПЕРАЦИОННЫЕ ПАУЗЫ (TRACKER_OPERATIONAL_WAIT_STATUSES):
  waiting_technician, waiting_parts, waiting_logistics, waiting_cs, deferred
  При этих статусах ответ staff НЕ переводит в waiting_client.

UI-подписи: STATUS_DISPLAY в constants.py.


3.2. Очередь v2 (queue_line, action_by, chat_turn, action_since)
────────────────────────────────────────────────────────────────
Логика: app/core/ticket_queue_state.py

queue_line — на какой линии ТП тикет:
  cs         — контакт-центр (1-я линия)
  engineers  — инженеры (2-я линия)
  partner    — партнёр (3-я линия)

action_by — у кого «мяч», кто должен действовать:
  cs, engineers, partner — staff должен ответить/обработать
  subscriber             — ждём абонента
  external               — внешняя пауза (запчасти, логистика)

chat_turn — коммуникационный ход в чате с абонентом:
  staff      — staff должен ответить («Нужен ответ»)
  subscriber — ждём сообщение абонента

action_since — timestamp начала ожидания (для сортировки очереди)


3.3. Правила v2 для source='lk'
───────────────────────────────

Абонент написал (on_subscriber_public_message):
  chat_turn      = 'staff'
  action_by      = queue_line (cs → 'cs', engineers → 'engineers')
  action_since   = NOW()
  last_client_message_at = NOW()
  status         → 'in_progress' (если был waiting_client/pending/open)

Staff ответил абоненту (on_staff_public_reply):
  chat_turn      = 'subscriber'
  action_by      = 'subscriber'
  action_since   = NOW()
  status         → 'waiting_client' (если НЕ ops-пауза и НЕ закрыт)

Эскалация на инженеров (on_escalate_to_engineers):
  queue_line     = 'engineers'
  action_by      = 'engineers' (сохраняет chat_turn если был staff)
  support_line   = 2
  status         = 'in_progress'

Возврат на КС (on_return_to_cs):
  queue_line     = 'cs'
  action_by      = 'cs'
  support_line   = 1

Внешняя пауза (on_external_wait):
  action_by      = 'external'
  chat_turn      = 'subscriber'
  reconcile НЕ перезаписывает v2 пока action_by='external'


3.4. Колонка «Статус» в списке /tickets (коммуникационный слой)
───────────────────────────────────────────────────────────────
Вычисляется функцией communication_state_from_v2() — НЕ равен raw status:

  chat_turn='staff' AND action_by IN (cs, engineers, partner)
    → communication_state = 'needs_reply'     («Нужен ответ»)

  chat_turn='subscriber' AND source='lk'
    → communication_state = 'awaiting_subscriber' («Ждём абонента»)

  action_by='external'
    → показывается workflow-status (waiting_parts и т.д.)

  Закрытые тикеты
    → workflow-status (STATUS_DISPLAY)


3.5. Подсветка строки (list_highlight)
──────────────────────────────────────
Функция list_highlight_for_viewer() в ticket_queue_state.py:

Для оператора КС на lk-тикете:
  list_highlight='chat' если chat_turn='staff' AND action_by IN (cs,engineers,partner)
  (КС видит «нужен ответ» даже если тикет на линии инженеров)

Дополнительно: has_unread=true на своей линии → 'chat'

4. ПЕРЕХОДЫ СОСТОЯНИЙ ПРИ ДЕЙСТВИЯХ (source='lk')
================================================================================

4.1. Абонент создаёт тикет (ЛК, вне helpdesk)
─────────────────────────────────────────────
Ожидаемые INSERT/UPDATE:

  tracker_tickets:
    source='lk', user_id=абонент, title, body
    status='pending' или 'open'
    support_line=1, queue_line='cs'
    action_by='cs', chat_turn='staff', action_since=NOW()
    object_type='user', person_type='user'

  user_mail: первое сообщение (answer=0, person_type='user', ticket_id)

  tracker_ticket_line_history:
    сегмент support_line=1, state='active'
    событие event_type='created', payload={status, source:'lk'}

  (опционально) tracker_ticket_mail_links — только если ticket_id не в mail


4.2. Абонент пишет в существующий тикет (ЛК)
────────────────────────────────────────────
  INSERT user_mail (от абонента)

  UPDATE tracker_tickets:
    chat_turn='staff'
    action_by=queue_line
    action_since=NOW()
    last_client_message_at=NOW()
    status='in_progress' (если был waiting_client)

  Пример:
    ДО:  action_by=subscriber, chat_turn=subscriber, status=waiting_client
    ПОСЛЕ: action_by=cs (или engineers), chat_turn=staff, status=in_progress


4.3. Оператор отвечает (helpdesk: POST /api/v1/helpdesk/tracker/{id}/messages)
───────────────────────────────────────────────────────────────────────────────
Функция send_mail_reply():

  INSERT user_mail (answer=1, person_type='skystream', user_id=operator_id)

  _apply_staff_chat_queue_update() → on_staff_public_reply():
    chat_turn='subscriber', action_by='subscriber', action_since=NOW()
    status → 'waiting_client' (если не ops-пауза)

  maybe_set_first_response_at() — если role=support и source=lk:
    first_response_at = NOW() (только первый раз)

  _maybe_claim_cs_assignee() — если role=support:
    assigned_to = operator_id, INSERT tracker_ticket_executors

  Пример:
    ДО:  action_by=cs, chat_turn=staff, status=in_progress
    ПОСЛЕ: action_by=subscriber, chat_turn=subscriber, status=waiting_client


4.4. Оператор открывает ленту / mark read
─────────────────────────────────────────
  INSERT user_mail_reads (msg_id, user_id, person_type='skystream')

  v2 и status НЕ меняются.
  has_unread может стать false, но «Нужен ответ» остаётся пока chat_turn='staff'.


4.5. Эскалация на инженеров (transfer-to-engineers)
────────────────────────────────────────────────────
  on_escalate_to_engineers()
  _change_ticket_support_line(1→2)
  tracker_ticket_line_history:
    закрытие сегмента support_line=1 (end_time)
    открытие сегмента support_line=2
    event_type='line_changed'
    event_type='escalated_to_engineers'
  Комментарий КС → tracker_comments (НЕ user_mail)


4.6. Возврат на КС (take-back-to-ks)
────────────────────────────────────
  on_return_to_cs()
  event_type='returned_to_cs', 'line_changed'


4.7. Закрытие тикета
────────────────────
  status='closed' (или resolved), date_of_close=NOW(), closed_by=operator_id
  _record_ticket_closed_history():
    закрытие активного сегмента линии (end_time)
    event_type='closed'
    event_type='status_changed' (trigger='close')


4.8. Переоткрытие (reopen, в течение 24ч)
─────────────────────────────────────────
  status → in_progress
  _record_ticket_reopened_history():
    новый сегмент линии
    event_type='reopened'
    event_type='status_changed' (trigger='reopen')


4.9. Reconcile (автосинхронизация v2 с лентой)
───────────────────────────────────────────────
Вызывается при:
  • открытии карточки тикета (load_ticket_detail)
  • загрузке списка /tickets (reconcile_open_tickets_on_list_page)

Функция reconcile_ticket_queue_from_thread():
  1. Берёт последнее сообщение из user_mail (по ticket_id + mail_links)
  2. Определяет from_subscriber (абонент или staff)
  3. Если v2 не соответствует последнему сообщению — пересчитывает snapshot
  4. Пропускает если action_by='external'

Зачем: если ЛК записал сообщение, но не обновил v2-поля — helpdesk подтянет
состояние при следующем просмотре оператором.

5. ИСТОРИЯ ТИКЕТА: users.tracker_ticket_line_history
================================================================================

5.1. Структура таблицы
──────────────────────
SQLAlchemy: TrackerTicketLineHistory (app/models/users.py)

  id              bigint PK
  ticket_id       bigint FK tracker_tickets ON DELETE CASCADE
  support_line    smallint nullable (1=КС, 2=инженеры, 3=партнёр, 4=менеджер)
  start_time      timestamptz
  end_time        timestamptz nullable
  changed_by      bigint → skystream_users.id
  event_type      varchar(50) nullable
  payload         jsonb nullable
  state           varchar(20) default 'active'
                  'active' — линия работает
                  'waiting_client' — ждём ответа абонента (legacy/пауза SLA)

Два типа записей:

  A) СЕГМЕНТЫ ЛИНИИ (support_line IS NOT NULL, event_type IS NULL):
     Фиксируют, на какой линии ТП находился тикет и когда.
     Активный сегмент: end_time IS NULL.
     При смене линии: закрывается старый сегмент (end_time=NOW), открывается новый.

  B) СОБЫТИЯ (support_line IS NULL, event_type IS NOT NULL):
     Точечные действия с payload.


5.2. Типы событий (event_type)
──────────────────────────────
  created               — создание тикета
                          payload: {status, source, connection_kind?}
  line_changed          — смена линии ТП
                          payload: {from_line, to_line}
  escalated_to_engineers— эскалация на инженеров
                          payload: {queue_line, action_by, chat_turn,
                                    action_since, from_line, to_line}
  returned_to_cs        — возврат на КС
                          payload: аналогично эскалации
  category_changed      — смена категории
                          payload: {from_category_id, to_category_id}
  closed                — закрытие
                          payload: {status, from_status}
  status_changed        — смена workflow-статуса
                          payload: {from_status, status, trigger}
                          trigger: 'close' | 'reopen' | ...
  reopened              — переоткрытие
                          payload: {from_status, status}

Для lk-тикетов, созданных в ЛК, ожидается запись created + сегмент support_line=1.
Helpdesk при register-call (call_center) пишет аналогично — эталон в tracker.py.


5.3. Функции записи истории (ticket_service.py)
───────────────────────────────────────────────
  _open_line_segment()           — новый сегмент линии (state='active')
  _close_active_line_segment()   — end_time на активном сегменте
  _change_ticket_support_line()  — close + open + event line_changed
  _add_line_history_event()      — точечное событие
  _record_ticket_closed_history()— close сегмент + closed + status_changed
  _record_ticket_reopened_history() — open сегмент + reopened + status_changed

HTTP API для просмотра истории в текущем helpdesk отсутствует
(есть только в legacy temp/router.py). Данные используются в stats_service.

Для справки при проектировании абонентского API (зеркальные операции).

8. ЧЕКЛИСТ ДЛЯ ТЗ АБОНЕНТСКОГО ЧАТА
================================================================================

Обязательные операции ЛК:

  [ ] Создание тикета: INSERT tracker_tickets (source='lk') + user_mail
  [ ] Отправка сообщения: INSERT user_mail (person_type='user', answer=0, ticket_id)
  [ ] UPDATE v2 при сообщении абонента (или полагаться на reconcile в helpdesk)
  [ ] UPDATE last_client_message_at
  [ ] Запись в tracker_ticket_line_history (created + сегмент линии)
  [ ] Чтение ответов staff из user_mail (person_type='skystream', answer=1)
  [ ] Прочтения: INSERT user_mail_reads (person_type='user') — для галочек у staff
  [ ] Вложения: user_mail_attachments
  [ ] Оценка закрытого тикета: tracker_tickets_ratings

НЕ делать в ЛК для публичного чата:

  [ ] INSERT в tracker_messages (это внутренний чат staff)
  [ ] Писать в tracker_comments (это только для операторов)

Согласованность с оператором:

  [ ] ticket_id на каждом user_mail (не только mail_links)
  [ ] person_type='user' на сообщениях абонента (не только answer=0)
  [ ] При ответе staff v2: chat_turn='subscriber' — абонент видит, что ждут его
  [ ] При сообщении абонента v2: chat_turn='staff' — оператор видит «Нужен ответ»
